QUELLENPRIORITÄT AB V5
----------------------
Die Inhalte aus MEMORY_ARCHITECTURE.zip stammen aus dem vom Benutzer selbst
gebauten und live verifizierten AutoTracker. Der Tracker ist für seinen
Snes9x-Hostspiegel funktional, aber seine als „kanonische WRAM-Offets“
bezeichneten Werte sind laut Mesen-Liveprüfung keine echten snesWorkRam-
Offsets. Sie dürfen deshalb nicht mehr ungeprüft Mesen/SNES-Bus-Adressen
überschreiben.

Innerhalb der ZIP gilt:
1. atomare Mesen-snesWorkRam-Liveprüfung = kanonische Spieladresse
2. src/helper/Core/Lufia2MemoryMap.cs = Snes9x-Hostspiegel-Layout
3. MEMORY_ARCHITECTURE.md = historische Trackerarchitektur
4. aktive DataReaders-/MemoryScanner-Logik = belegte Datengröße und Auswertung
5. emulator_addresses.json = nur historisches Hostadress-Archiv
6. statische JSON-Tabellen = Referenzdaten, sofern keine Speicheradresse genannt ist

PORTABLE ADRESSKONVENTION
-------------------------
Kanonisch wird der relative Offset im echten 128-KiB-SNES-WRAM-Block
verwendet. Er wird direkt über Mesens snesWorkRam oder über einen
emulatorspezifisch validierten WRAM-Reader ermittelt.

[!] Eine alte absolute Snes9x-Hostadresse darf NICHT generell durch Abzug
    einer angenommenen Basis in einen WRAM-Offset umgerechnet werden.
    Mesen-Liveprüfungen haben nichtlineare Hostspiegel belegt. Der häufige
    Versatz -0x2314 stimmt für mehrere gerenderte UI-Puffer, aber bereits der
    Save-Auswahlcursor ist ein Gegenbeispiel.

Mesen / SNES-Bus:
    Offset 0x00000–0x0FFFF -> 7E:0000–7E:FFFF
    Offset 0x10000–0x1FFFF -> 7F:0000–7F:FFFF

Alte Snes9x-Adressen bleiben ausschließlich Quellenhinweise. Jede daraus
abgeleitete Mesen-Adresse muss einzeln gegen sichtbaren Zustand plus echtes
snesWorkRam bestätigt werden. Abschnitt 54 ist daher ein historischer
Rechenabgleich und keine gültige Umrechnungstabelle.


MESEN-LIVE-KORREKTUR 2026-07-26
-------------------------------

[!] Die bisherigen Helper-Offets wie Gold 0x2D9E, Party 0x2D8F und Inventar
    0x2DA1 sind Offsets in einem Snes9x-Hostspiegel, nicht im echten SNES-WRAM.
    Direktes Lesen dieser Stellen in Mesens snesWorkRam liefert unmögliche
    Werte, z. B. Party 18 58 18 5A.

    echter Mesen-Offset = bisheriger Helper-Offset - 0x2314

ist weiterhin keine globale Umrechnung beliebiger alter Hostadressen.

52. PORTABLE WRAM- UND ROM-BASISERKENNUNG AUS DEM HELPER
========================================================

WRAM:
[x] vollständiger SNES-WRAM-Block = 0x20000 Bytes
[x] absolute Prozessadresse = erkannte WRAM-Basis + relativer Offset
[x] Goldanker: WRAM-Basis = absolute Goldadresse - 0x2D9E
[x] Signaturanker:
    „SSelan“ gefunden -> WRAM-Basis = Fundadresse - 0x2F7E
    „AArty“ gefunden  -> WRAM-Basis = Fundadresse - 0x30FE
    „LLexis“ gefunden -> WRAM-Basis = Fundadresse - 0x3326
[x] Scanner prüft Lesbarkeit bei WRAM+0x00000 und WRAM+0x1FFFF.

ROM:
[x] absolute ROM-Prozessadresse = erkannte ROM-Basis + linearer ROM-Offset
[x] Header-/Titelsignatur liegt laut Scanner bei ROM+0xFFC0.
[x] Capsule-Sprite-Tabelle wird bei ROM+0xBDCB8 erwartet und zur Korrektur
    einer gefundenen ROM-Basis verwendet.
[ROM] ItemTableBase       = ROM+0xB4F69
[ROM] SpellPointerTable   = ROM+0xAFAAB
[ROM] ShopDirectoryBase   = ROM+0xBEE9F
[ROM] ShopOffset          = ROM+0xBF09F
[ROM] IPSkillTable        = ROM+0xDE0C5–0xDEB9C
[ROM] CapsuleSpriteOffset = ROM+0xBDCB8

[PROC] x64 PointerBaseAddress 0xA52330:
    Bezogen auf die beobachtete x64-WRAM-Basis 0xA30000 liegt dieser
    Speicherplatz bei +0x22330 und damit außerhalb des 0x20000-Byte-WRAM.
    Er ist ein emulatorabhängiger Pointer-Speicherplatz, kein WRAM-Offset.
    Das NWA-Profil verwendet mit 0xBA0598 einen völlig anderen Ort.
    Nicht in eine portable WRAM-Map übernehmen; stattdessen ROM-Basis scannen.


53. DATENTYPEN UND LIVE-TRACKER-AUSWERTUNG
==========================================

KANONISCH UND LIVE VERIFIZIERT
------------------------------
[x] WRAM-Größe: 0x20000 Bytes.
[x] Gold 7E:2D9E: uint24 little-endian; gültiger Scannerbereich 0–9.999.999.
[x] Party 7E:2D8F–7E:2D92: vier uint8-IDs.
    00 Maxim, 01 Selan, 02 Guy, 03 Artea, 04 Tia, 05 Dekar, 06 Lexis, FF leer.
    Nichtleere IDs müssen für die Scannervalidierung eindeutig sein.
[x] Scenario 7E:2C32–7E:2C34: exakt drei Bytes.
[x] Capsule-Fundstatus Mesen 7E:11BB–7E:11C1: sieben einzelne Bytes.
    Legacy-Helper 7E:34CF–7E:34D5 war ein Snes9x-Hostspiegel-Layout.
    Im Randomizer keine feste Capsule-Identität pro Position annehmen.
[x] Dungeonflags 7E:2A96–7E:2A9F: zehn Bytes.
[x] Transport 7E:2CF5: uint8.
    FF wird als Ship/Airship ausgewertet.
    00–05 gelten beim Scanner als plausible Transportwerte; der aktuelle
    Positionsreader behandelt alle Werte außer FF als Walk.
[x] Lauf-X = (7E:3780 << 8) | 7E:377F.
[x] Lauf-Y = (7E:3783 << 8) | 7E:3782.
[x] Ship-X = (7E:379D << 8) | 7E:379C.
[x] Ship-Y = (7E:37A0 << 8) | 7E:379F.
[x] Karten-/Ebenen-ID: Mesen 7E:05AC, uint8.
[x] Herkunftskarte: Mesen 7E:05AE, uint8.
[x] Inventar: 191-Byte-Datenstrom [7E:2DA1, 7E:2E60).
[x] Normalwerkzeuge werden als Little-Endian-Bytefolge an beliebiger Position
    im Inventardatenstrom gesucht.
[x] Capsule-ROMtabelle: ROM+0xBDCB8, sieben Einträge, Stride 10 Bytes;
    je Eintrag werden die ersten zwei Bytes als Spritewert gelesen.
